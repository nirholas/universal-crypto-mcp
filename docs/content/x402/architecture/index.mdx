# x402 Architecture

Complete architectural overview of the x402 payment protocol - enabling AI agents to automatically pay for APIs.

## System Overview

```

│                        x402 Ecosystem                            │
└─────────────────────────────────────────────────────────────────┘
```

## Core Components

### 1. Client (AI Agent)

**Purpose**: Initiate requests and handle payment requirements

**Key Responsibilities**:
- Detect 402 responses
- Construct payment transactions
- Sign and submit payments
- Retry requests with payment proof

**Implementation**:
```typescript
┌─────────────────────────┐
│   x402Client            │
├─────────────────────────┤
│ - wallet: Wallet        │
│ - httpClient: HTTP      │
│ - mechanism: Mechanism  │
├─────────────────────────┤
│ + request()             │
│ + handlePayment()       │
│ + retryWithProof()      │
└─────────────────────────┘
```

**Supported in**:
- TypeScript (Axios, Fetch wrappers)
- Python (httpx, requests)
- Go (net/http)
- Java (HttpClient)

## Payment Flow

### Complete Request-Response Cycle

```

   │ Client  │                          │ Server  │
   └────┬────┘                          └────┬────┘
        │                                     │

        ├────────────────────────────────────>│
        │                                     │
        │  2. 402 Payment Required            │
        │     {                               │
        │       amount: "0.01",               │
        │       chain: "arbitrum",            │
        │       token: "USDC",                │
        │       recipient: "0x123...",        │
        │       nonce: "abc123"               │
        │     }                               │
        │<────────────────────────────────────┤
        │                                     │
    ┌───┴───┐                                 │
    │ Check │                                 │
    │ wallet│                                 │
    │balance│                                 │
    └───┬───┘                                 │
        │                                     │
    ┌───┴────┐                                │
    │ Create │                            ┌───┴────┐
    │payment │                            │ Wait   │
    │   TX   │                            │for     │
    └───┬────┘                            │payment │
        │                                 └───┬────┘
        │  3. Submit to blockchain           │
        ├────────────────────────────────────┤
        │     (Blockchain Layer)             │
        │       ▼ ▼ ▼ ▼ ▼                   │
        │       Transfer 0.01 USDC           │
        │       from client to server        │
        │       ▲ ▲ ▲ ▲ ▲                   │
        │                                    │
        │  4. GET /api/data                  │
        │     Headers:                       │
        │       X-Payment-TX: 0xabc...       │
        │       X-Payment-Nonce: abc123      │
        ├───────────────────────────────────>│
        │                                    │
        │                                ┌───┴────┐
        │                                │ Verify │
        │                                │payment │
        │                                │on-chain│
        │                                └───┬────┘
        │                                    │
        │  5. 200 OK + Data                  │
        │     { premium: "content" }         │
        │<───────────────────────────────────┤
        │                                    │
        ▼                                    ▼
```

### Detailed Steps

#### Step 1: Initial Request
```http
GET /api/premium-data HTTP/1.1
Host: api.example.com
```

Client makes normal HTTP request without payment.

#### Step 2: Payment Required Response
```http
HTTP/1.1 402 Payment Required
Content-Type: application/json
X-Payment-Required: true

{
  "error": "Payment Required",
  "payment": {
    "chain": "arbitrum",
    "token": "USDC",
    "amount": "10000", // 0.01 USDC (6 decimals)
    "recipient": "0x742d35Cc6634C0532925a3b844Bc9e7595f0bEb",
    "nonce": "req_20260131_abc123",
    "deadline": 1738368000 // Unix timestamp
  },
  "message": "Pay 0.01 USDC to access this endpoint"
}
```

Server indicates payment is required and provides payment details.

#### Step 3: Client Processes Payment

```typescript
// Client automatically:
1. Parses 402 response
2. Checks wallet balance (>= 0.01 USDC)
3. Constructs payment transaction
4. Signs transaction
5. Submits to blockchain
6. Waits for confirmation
```

**Transaction Details**:
```solidity
// On Arbitrum
transferFrom(
  from: 0x...client,
  to: 0x742d...recipient,
  amount: 10000 // 0.01 USDC
)

// Returns transaction hash: 0xabcdef...
```

#### Step 4: Retry with Payment Proof
```http
GET /api/premium-data HTTP/1.1
Host: api.example.com
X-Payment-TX: 0xabcdef1234567890...
X-Payment-Nonce: req_20260131_abc123
```

Client retries request with payment proof headers.

#### Step 5: Server Verifies and Responds

```typescript
// Server automatically:
1. Extracts payment proof headers
2. Queries blockchain for transaction
3. Verifies:
   - Transaction exists
   - Amount matches (0.01 USDC)
   - Recipient matches
   - Nonce matches
   - Not expired
   - Not previously used
4. If valid: Grant access
5. If invalid: Return 402 or 400
```

**Success Response**:
```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "data": "Premium content here",
  "payment": {
    "verified": true,
    "txHash": "0xabcdef...",
    "amount": "0.01",
    "timestamp": 1738368000
  }
}
```

## Security Architecture

### Payment Verification

```typescript
┌────────────────────────────────────────┐
│     Payment Verification Process       │
└────────────────────────────────────────┘

1. ┌─────────────────────┐
   │ Extract TX Hash     │
   └──────────┬──────────┘
              │
2. ┌──────────▼──────────┐
   │ Query Blockchain    │ ← RPC call to verify on-chain
   └──────────┬──────────┘
              │
3. ┌──────────▼──────────┐
   │ Verify Amount       │ ← amount == expected
   └──────────┬──────────┘
              │
4. ┌──────────▼──────────┐
   │ Verify Recipient    │ ← to == server address
   └──────────┬──────────┘
              │
5. ┌──────────▼──────────┐
   │ Verify Nonce        │ ← nonce == request nonce
   └──────────┬──────────┘
              │
6. ┌──────────▼──────────┐
   │ Check Not Expired   │ ← timestamp < deadline
   └──────────┬──────────┘
              │
7. ┌──────────▼──────────┐
   │ Check Not Reused    │ ← nonce not in used_set
   └──────────┬──────────┘
              │
8. ┌──────────▼──────────┐
   │ Mark Nonce Used     │ ← prevent double-spending
   └──────────┬──────────┘
              │
   ┌──────────▼──────────┐
   │   Grant Access ✓    │
   └─────────────────────┘
```

### Attack Prevention

#### 1. Double-Spend Protection
**Problem**: Attacker reuses same payment for multiple requests  
**Solution**: Nonce tracking (each payment has unique nonce, tracked in database)

```typescript
const usedNonces = new Set<string>()

function verifyPayment(tx: string, nonce: string) {
  if (usedNonces.has(nonce)) {
    throw new Error('Payment already used')
  }
  // ... verify transaction ...
  usedNonces.add(nonce)
}
```

#### 2. Replay Attack Protection
**Problem**: Attacker captures and replays payment proof  
**Solution**: Short expiration times (5-15 minutes)

```typescript
payment: {
  deadline: Date.now() + 15 * 60 * 1000, // 15 minutes
  nonce: `req_${Date.now()}_${randomBytes(16)}`
}
```

#### 3. Amount Manipulation
**Problem**: Attacker pays less than required  
**Solution**: Strict on-chain amount verification

```typescript
const txAmount = await getTransactionAmount(txHash)
if (txAmount < requiredAmount) {
  throw new Error('Insufficient payment')
}
```

#### 4. Front-Running
**Problem**: MEV bot sees payment and extracts value  
**Solution**: Private transaction submission (Flashbots, Eden, etc.)

```typescript
// Use private RPC for sensitive payments
const provider = new FlashbotsProvider(rpcUrl)
await provider.sendPrivateTransaction(signedTx)
```

### High-Throughput Design

```

│           x402 Scalability Layers                │

│Server 1│  │Server 2│  │Server 3│  │Server N│
└───┬────┘  └───┬────┘  └───┬────┘  └───┬────┘
    │           │           │           │
    └───────────┴───────────┴───────────┘
                    │
Layer 2: Shared Payment Cache
         ┌──────────▼──────────┐
         │   Redis Cluster     │
         │  (Payment Proofs)   │
         └─────────────────────┘

Layer 3: Blockchain Read Replicas
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │ RPC  #1 │  │ RPC  #2 │  │ RPC  #N │
    └────┬────┘  └────┬────┘  └────┬────┘
         │            │            │
         └────────────┴────────────┘
                     │
Layer 4: Blockchain Layer
         ┌───────────▼────────────┐
         │  Arbitrum / Solana     │
         │  (On-chain Settlement) │
         └────────────────────────┘
```

### Performance Optimizations

#### 1. Payment Proof Caching
```typescript
// Cache verified payments for 1 hour
const cache = new Redis()

async function verifyPayment(txHash: string) {
  const cached = await cache.get(`payment:${txHash}`)
  if (cached) return JSON.parse(cached)
  
  const verified = await blockchainVerify(txHash)
  await cache.setex(`payment:${txHash}`, 3600, JSON.stringify(verified))
  
  return verified
}
```

**Benefit**: Reduce blockchain queries by 95%

#### 2. Batch Verification
```typescript
// Verify multiple payments in single RPC call
async function verifyBatch(txHashes: string[]) {
  const requests = txHashes.map(hash => ({
    method: 'eth_getTransactionReceipt',
    params: [hash]
  }))
  
  const results = await provider.batchRequest(requests)
  return results.map(verifyReceipt)
}
```

**Benefit**: 10x faster for high-volume APIs

#### 3. Async Verification
```typescript
// Return immediately, verify in background
app.post('/api/data', async (req, res) => {
  const txHash = req.headers['x-payment-tx']
  
  // Return data immediately
  res.json({ data: 'content' })
  
  // Verify asynchronously
  verifyPaymentAsync(txHash).catch(err => {
    // Revoke access if verification fails
    revokeAccess(req.ip, txHash)
  })
})
```

**Benefit**: <10ms response time (vs 2000ms synchronous)
